# 试点数据准备包

本包承接最新指导，补充真实数据协调、系统联调和论文验证的准备工作。现有问答、预审、专家审核、终审、文档中心、趋势和图谱功能继续保留。每年约60个立项项目是规模参考，不是系统容量限制或申报总量。

本目录三个 CSV 都只有表头，没有真实数据。它们是资料收集模板，**当前不能直接通过现有专家/文献导入入口导入**，也没有启用新的项目推送接口。填好后的真实台账、原件和验收记录保存在经授权的内部位置，不回填本仓库模板。

## 一、先协调哪些数据

| 优先级 | 数据 | 用途 | 准备要求 |
|---|---|---|---|
| 第一批 | 一个完整年度的项目台账 | 地域、单位、年度分布及项目定位 | 尽量包含全部申报项目；只有立项项目时明确范围 |
| 第一批 | 少量获授权的申报材料及各版补正稿 | 解析、知识检索、预审和证据核对 | 首批可选5–10个不同格式、长短和完整度的项目开展功能验证；不据此宣称整体准确率 |
| 第一批 | 对应申报指南、审核清单与公开政策 | 提供审核依据和问答证据 | 记录来源、文号、适用年度和版本；现有系统不自动判断政策时效 |
| 第二批 | 专家意见、合同、进展、变更、验收材料 | 复用现有案卷和材料版本，形成项目历史 | 每份材料有稳定项目编号、材料角色和版本 |
| 第二批 | 有明确依据及授权的诚信记录 | 管理员核对事实与评价依据 | 区分待核实线索与正式认定，规则确定后再实现评价 |
| 联调时 | 系统账号标识、单位标识、项目访问授权 | 对接科研管理系统身份和权限 | 两类业务用户先与现有四角色做映射；不能把申报用户直接映射为可读全库的现有角色 |

## 二、项目台账字段

模板：[项目台账模板.csv](项目台账模板.csv)。每行一个独立项目，不按文件数量重复计数。

| 字段 | 是否必填 | 含义 |
|---|---|---|
| project_id | 是 | 来源系统稳定项目编号；跨版本保持不变，不能用标题代替 |
| title | 是 | 项目名称 |
| application_year | 是 | 申报年度，四位数字；与起止年、立项年分别记录 |
| application_batch | 建议 | 申报批次或指南 |
| project_type | 建议 | 来源系统的项目类别原值 |
| region_code / region_name | 至少名称 | 申报地区的代码和名称，注明按单位所在地还是申报归属地统计 |
| institution_code / institution | 至少名称 | 申报单位稳定代码和原名；不自动合并简称、分院或上下级单位 |
| official_status | 是 | 来源系统状态原值，不使用本系统材料体检状态代替 |
| status_date | 建议 | 状态日期，YYYY-MM-DD |
| approval_year | 有立项记录时 | 立项年度；未知留空，不能从文件年份猜测 |
| amount_wan | 可选 | 经费，单位万元；未知留空，不能用0代替缺失 |
| source_system / source_record_id | 是 | 来源系统及其记录标识，供去重与追溯 |
| source_updated_at | 建议 | 来源更新时间，带时区；用于后续同步增量 |
| coverage_scope | 是 | all_applications（全部申报）、approved_only（仅立项）、partial（部分记录） |
| authorization_ref | 是 | 内部授权或数据提供单的引用编号，不填密钥、个人证件或口令 |

口径：缺失地区和单位单列“未提供”；同一项目补正不新增项目数。若同一来源编号对应多行，应先确认是变更事件还是重复记录。立项率只能在同一年度、批次和完整申报范围内计算，只有立项数据时仅展示立项数量与分布。

现有 `ProjectRecord` 只预留部分项目字段，上述年度、地区、授权等是待对接的采集字段；本包不会改动已冻结契约。现有 `dossiers.phase` 表示材料阶段，`review_cases.stage` 表示本地评审阶段，均不替代官方项目状态。

## 三、材料清单字段

模板：[材料清单模板.csv](材料清单模板.csv)。一份材料的一个版本对应一行；文件通过内部安全渠道另行提供。

| 字段 | 是否必填 | 含义 |
|---|---|---|
| material_id / project_id | 是 | 材料编号、所属项目编号；project_id须在项目台账中存在 |
| material_role | 是 | 优先复用 `rag/dossiers.py` 的材料角色，如 proposal_text、integrity_pledge、contract、expert_opinion、achievement_report |
| filename / format | 是 | 文件名和实际格式，格式如 docx、pdf、pptx；模板不存原件 |
| version / is_current | 是 | 版本号、是否当前稿（true/false）；同项目同角色仅一份当前稿 |
| source_date | 建议 | 材料形成日期，不用上传时间替代 |
| sha256 | 建议 | 原件完整性校验值，64位十六进制；不证明内容真实或来源合法 |
| readable_text | 是 | yes、no、unknown；扫描件、图片型PPT需单独验证 |
| source_record_id / authorization_ref | 是 | 来源记录及内部授权引用 |

当前支持的文档格式以 `/api/health` 的 `upload_types` 为准；PPTX与旧PPT要区分，不能把后缀改名当作格式转换。扫描PDF和图片型页面不承诺可读取；复杂表格、文本框顺序和页码保真需人工抽查。

数据库接入是结构化数据同步，不是上传文件。测试联调先确认只读视图或导出字段、稳定ID和更新规则，再复用现有接入层；不能直接连生产数据库写入。

## 四、测试系统联调与验收

模板：[试点验收记录模板.csv](试点验收记录模板.csv)。每条结果必须记录实际观察，未执行写“未执行”，不预填通过。

最小联调顺序：

1. 测试环境提供内网入口、模型端点与身份接入方式，确认是否采用嵌入页、独立窗口或系统内智能体入口。
2. 使用测试账号验证申报用户只能读取授权项目，管理员按授权范围查看；服务端检查权限。当前四角色并不提供申报用户的项目级隔离，这一项需后续实现再验收。
3. 使用同一项目编号串起原件、预审、专家意见、终审及版本归档，回到文档中心核对证据。
4. 分别验证可编辑DOCX、文本PDF、扫描PDF、PPTX、表格文档和损坏文件；记录成功、提示与人工处理路径。
5. 验证模型不可用、超时、重复提交、网络中断、材料更新后旧证据仍能定位。
6. 管理员按项目台账手工复算年度、地区和单位数量；统计页尚未实现，不能将人工核对结果写成页面已通过。

建议每个验收项记录：case_id、requirement、source_project_id、input_format、actor_role、expected、actual、result、evidence_ref、tested_at、tester_alias。验收附件只保留在内部测试目录，测试结果不使用真实姓名作公开标识。

## 五、现有功能如何承接

| 新指导 | 可复用部分 | 后续需要业务确认 |
|---|---|---|
| 智能体问答 | 问答、模型来源快照、引用深链、知识库 | 申报用户的资料可见范围 |
| 用户项目审核 | 项目预审、查重依据、补正问题、归档 | 是自查还是正式审核；由谁提交和签署 |
| 科研诚信评价 | 政策证据、回避依据、操作留痕 | 评价对象、指标、依据和人工确认，不能直接把查重相似度当诚信分 |
| 项目历史沿革 | 历史课题、材料版本、多轮案卷 | 官方立项、变更、验收事件的来源与状态映射 |
| 知识库与知识图谱 | 文档中心、关键词星图、来源摘录 | 管理员维护范围；现有图谱不自动等同项目关系网络 |
| 地域、单位分析 | 项目台账准备、单位原名及保守归一原则 | 全量申报范围、地区定义与统计口径 |
